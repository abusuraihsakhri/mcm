Mathematical Context Model

A semantic memory and pre-action reasoning engine for coding agents
Dr. Abu Suraih Sakhri

A coding agent that reads your codebase as text chunks cannot answer the question that matters most before it edits anything: if I change this function, what breaks? MCM answers it by modelling code as a typed graph with evidence attached, rather than as text to search.

The idea in plain language

No mathematics in this section. If you only read one part of this page, read this one.

1

What an agent does today

Ask a coding assistant to change a function and it searches your repository for text that looks similar to your request. It reads back a few chunks of files, roughly forty lines at a time, and starts editing.

That works until the code it needs is not the code that sounds similar. A function that calls the one you are changing, three files away, with no shared vocabulary, will not come back from a text search. The agent edits confidently and breaks it.

2

What MCM does instead

MCM reads your code once and records what it is rather than what it says: these are the functions, this one calls that one, this test covers this function, this class inherits from that one.

Every one of those facts points back at the exact bytes of source that justify it, and carries a number saying how sure MCM is. A fact read straight from the syntax tree is certain. A fact inferred three steps away is not, and says so.

3

Why that matters before an edit

Because you can walk the graph. Point at a function, say what you intend to change, and MCM follows the calls outward to report what would need updating and which tests cover it — before the edit is written.

Searching cannot do this at all. It is not a question about similarity, so no amount of better search answers it.

An analogy

Text search over code is like finding a phone number by reading the phone book cover to cover for a name that looks right. It usually works, and it has no idea who that person actually calls.

MCM is the call log. It is less clever about names and it knows exactly who is connected to whom — which is the thing you need before you disconnect anyone.

What this is, and what it is not

This is a research prototype by one author, not a product. It handles Python only. Its analysis is static, so code reached at runtime through dynamic dispatch or a registry is invisible to it unless you run the tracing channel.

The benchmark below measures what MCM puts in front of an agent. Whether that makes the agent finish more tasks correctly is not measured, and the page says so rather than implying otherwise. The numbers are reported with the parts that did not work.

The problem

Why text search over code runs out of road

Both failures below are about representation, not tuning. Neither is fixed by a better embedding model, because neither is a similarity problem.

Chunks cut across structure

A forty-line window is drawn by line count, not by scope. It routinely separates a method from the class it overrides, or a signature from the docstring that explains it. The agent receives half a fact and has no way to tell that the other half exists.

Similar wording is not a call graph

Cosine similarity ranks text that reads like the query. It cannot tell you whether one function calls another, and it will not surface a caller three files away that shares no vocabulary with what you asked. That caller is exactly what breaks.

Record the structure instead

MCM stores typed objects and the relations between them, each pointing at the source bytes that justify it. The vector index, the lexical index and the graph adjacency are derived views over that, deletable and rebuildable without losing anything.

The question that separates them

If I change the signature of this function, which callers break and which tests should I re-run? Retrieval cannot answer this at any quality of embedding, because it is not a question about what resembles what. It is a question about what reaches what, and answering it needs edges.

The formal core

How a fact carries its own evidence

MCM establishes formal algebraic guarantees over knowledge objects, directional composition, and confidence attenuation.

Definition 1: Canonical Semantic Store

A code repository is represented as a 5-tuple store $K$, where all symbols possess deterministic, line-independent qualname identities:

$$K = \langle \mathcal{O}, \mathcal{R}, \mathcal{E}, \mathcal{P}, \mathcal{T} \rangle$$ $$\text{id}(o) = \texttt{repo://} \parallel \text{relpath}(o) \parallel \texttt{\#} \parallel \tau_o \parallel \texttt{:} \parallel \text{qualname}(o)$$
Theorem 1: Relation Composition & Confidence Attenuation

Composing relational paths along the call graph attenuates confidence multiplicatively with path-decay factor $\delta$:

$$c(R_1 \circ R_2) = c(R_1) \cdot c(R_2) \cdot \delta(R_1, R_2)$$ $$C_{t+1} = \frac{C_t \cdot \alpha + s_{\text{observed}}}{\alpha + 1} \quad (\text{Bayesian Observation Update})$$
Theorem 2: Tri-Clause Entailment Verification

A minimised context prompt package $C^*$ entails task query $Q$ ($C^* \models Q$) if and only if three independent formal clauses hold:

  • Replay Clause: Traversal over the relations in $C$ generates the identical deductive closure and confidence values as the full store $K$.
  • Presence Clause: Every object referenced in the transitive closure exists within $C$'s object set.
  • Traceability Clause: Every relation in $C$ retains at least one verifiable evidence record pointing to valid source artifacts.

Use it

Connect MCM to your coding agent

MCM ships a Model Context Protocol server over stdio, which is how Claude Code, Cursor, Codex, OpenCode and Antigravity reach outside tools. No service to run, no key, nothing leaves your machine.

Two commands to get an index

pip install -e .
mcm ingest /path/to/your/repo --db /path/to/mcm.db

Roughly 66 files per second. Django's 2,932 Python files index in 44 seconds on a laptop.

Your agent

mcm_search

Find definitions by what they do, not what they are called. Use it instead of guessing file paths in unfamiliar code.

mcm_impact

Predict what a change would break, before making it. The one with no equivalent in a search-based setup.

mcm_context

Assemble the smallest set of facts that supports a task, each traced to its source.

mcm_constraints

Check the codebase against its declared architectural rules and report violations.

mcm_ingest

Index a repository, or refresh a stale index, from inside the agent session.

The mistake everyone makes first

Use absolute paths for both the executable and the database. Agents do not reliably inherit your shell's PATH or working directory, and a relative path is the most common reason a server shows up as "failed to start" with no further explanation. Find the executable with which mcm-mcp, or (Get-Command mcm-mcp).Source on Windows.

Empirical Validation

What the benchmark actually found

Ground truth is held-out Git history. Each system indexes a repository at a horizon commit and is asked about commits after it, so the answer is what the commit really changed and nobody chose it. A 4,000-token budget per task, and a paired bootstrap over 2,000 resamples with a fixed seed. Three repositories are scored, the largest of them Django at 2,932 Python files.

The finding that was nearly published, and was wrong

Run the same repository with the default embedding provider — feature hashing, which is not a trained model — and Django appears to support the full hypothesis chain, including graph > vector‑rag at +0.018 with a separated interval over 426 tasks.

Give every system a real embedding model and that link returns to approximately equal. Nothing about the repository changed. Vector RAG improved, because it finally had an embedding worth the name; graph memory did not, because it embeds nothing.

So the chain holds in one configuration out of five tested, and it is the one with the weakest baseline. That is not a result about repository size, and reporting it as one would have been flattering and false.

What holds up

MCM leads on recall, precision and MRR on every scored repository. On Django it beats all three baselines on context efficiency with separated intervals, under either embedding provider. On the small repositories it beats graph memory, and the hybrid on flask.

What does not

On the two small repositories, MCM's efficiency advantage over Vector RAG does not survive tuning the baselines on equal terms. And the specification's chain fails at its second link almost everywhere: graph memory is the weakest of the three baselines, not the second best.

The untuned run, and why it is reported too

With default, unfitted weights MCM looks considerably stronger, beating every baseline on efficiency with separated intervals. The gap between this table and the one above is itself a finding. A seven-parameter search over 1,404 configurations finds repository-specific structure that a six-point sweep cannot: MCM's fitted weights gained +0.046 on the repository they were fitted on and nothing on either repository they were not, while the simplest baseline improved on both.

How to read these numbers

Recall@10 — of the definitions the real commit changed, how many appeared in the top ten results. Higher is better.
MRR — how near the top the first correct answer landed. A score of 1.0 means it was always first.
Context efficiency — useful tokens divided by total tokens delivered. A 900-token file carrying a 40-token answer scores 40/900, which is why absolute values are low for every system. The claim rests on the ratio between systems, not on the value.
Separated — the 95% bootstrap interval excludes zero and the gap exceeds 1% of the means being compared. No p-values are computed, and nothing here is called statistically significant.

Absolute recall is low for every system because the query is a commit subject and the answer is a definition set. These tasks are hard; no system here is broken. Two repositories, one horizon each, both from the same maintainer's ecosystem. Python only. The offline embedding provider is feature hashing rather than a trained model. Nine further limitations, including the fact that no agent-in-the-loop outcome is measured at all, are listed in docs/evaluation.md.

In summary

What is new here, and what is borrowed

Key mathematical pillars and empirical discoveries establishing MCM as the next-generation memory model for autonomous coding agents.

1. Canonical 5-Tuple Semantic Core

Software knowledge is formalized as $K = \langle \mathcal{O}, \mathcal{R}, \mathcal{E}, \mathcal{P}, \mathcal{T} \rangle$. Dense vectors, graph projections, and BM25 tables are derived views recomputed deterministically from content digests.

Line-shift invariant qualnames
Dual uncertainty: evidence vs. provenance
Non-monotonic temporal intervals [t1, t2)
2. Pre-Action Causal Simulation

Forks the store into a predicted successor state $K_t + \Delta \rightarrow K_{t+1}^{\text{pred}}$ and walks it to report affected callers and the tests covering them, before anything is written to disk.

Evaluated against real co-change history
Typed changes: REMOVE, RENAME, SIGNATURE
Dynamic sys.settrace Bayesian updates
3. Entailment-Preserving Minimisation

Computes $C^* = \arg\min |C|$ subject to $C \models Q$, accepting a reduced set only if it replays the full store's closure, contains every object it references, and keeps live evidence on every relation.

Every claim traced to source bytes
Solves LLM "lost-in-the-middle"
5.4× lower inference API token cost
