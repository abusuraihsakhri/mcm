Code is more than text.

MCM gives coding agents a typed model of what code elements are, how they depend on one another, what evidence supports those links, and when those facts were true—so context can be retrieved and change impact reasoned about before an edit.

01 / IDEA

A coding agent needs relevance and consequence.

Search is good at finding code that resembles a request. Editing safely also requires knowing what depends on the code being changed. MCM keeps those two problems distinct and lets them work together.

Semantic relevance

What code looks related to the task?

Vector and lexical retrieval are useful for locating definitions when names and wording are uncertain. MCM keeps these channels.

“Where is token validation implemented?”
Structural consequence

What code is connected to the thing I may change?

This needs explicit relations: calls, imports, tests, inheritance, evidence and time. MCM stores those relations rather than asking similarity to stand in for them.

“If I change this signature, which callers and tests matter?”

MCM is not a replacement for retrieval. It is a canonical context layer underneath retrieval and change analysis: typed objects and relations are primary; vector, lexical and graph indexes are rebuildable projections.

02 / FLOW

One proposed edit becomes a traceable context package.

The central workflow is pre-action: resolve the target, traverse what the change can reach, attach evidence, then assemble only the context the agent needs.

Proposed change Signer.sign(value, key=None) + algorithm="sha256"
  1. Resolve

    Map the request to a stable symbol identity rather than a line-number chunk.

  2. Propagate

    Walk typed relations from the target and attenuate confidence as paths get longer.

  3. Ground

    Keep the source bytes and provenance that justify every relation surfaced to the agent.

  4. Minimise

    Build a bounded context set that still reproduces the relevant closure and keeps its evidence.

  5. Act

    Expose the result through CLI, REST or MCP before the agent edits the repository.

03 / MODEL

The canonical store keeps meaning, evidence and time together

A repository is represented as objects, relations, evidence, provenance and temporal validity. Retrieval indexes and graph adjacency are derived from this store and can be rebuilt.

Definition 1: Canonical Semantic Store

A code repository is represented as a 5-tuple store $K$, where all symbols possess deterministic, line-independent qualname identities:

$$K = \langle \mathcal{O}, \mathcal{R}, \mathcal{E}, \mathcal{P}, \mathcal{T} \rangle$$ $$\text{id}(o) = \texttt{repo://} \parallel \text{relpath}(o) \parallel \texttt{\#} \parallel \tau_o \parallel \texttt{:} \parallel \text{qualname}(o)$$
Relation composition and confidence attenuation

Composing relational paths along the call graph attenuates confidence multiplicatively with path-decay factor $\delta$:

$$c(R_1 \circ R_2) = c(R_1) \cdot c(R_2) \cdot \delta(R_1, R_2)$$ $$C_{t+1} = \frac{C_t \cdot \alpha + s_{\text{observed}}}{\alpha + 1} \quad (\text{Bayesian Observation Update})$$
Context reduction must preserve support

A minimised context prompt package $C^*$ entails task query $Q$ ($C^* \models Q$) if and only if three independent formal clauses hold:

  • Replay Clause: Traversal over the relations in $C$ generates the identical deductive closure and confidence values as the full store $K$.
  • Presence Clause: Every object referenced in the transitive closure exists within $C$'s object set.
  • Traceability Clause: Every relation in $C$ retains at least one verifiable evidence record pointing to valid source artifacts.

05 / USE IT

Index locally, then expose MCM as an agent tool

The default indexer and hashed embedding provider are local. The MCP server runs over stdio, so an agent can query the same store without a separate service.

1. Create the index

git clone https://github.com/abusuraihsakhri/mcm.git
cd mcm
python -m venv .venv
pip install -e ".[dev,api]"

mcm ingest /path/to/repo --db mcm.db
mcm index --db mcm.db

Current repository measurements report roughly 66 files/s; Django’s 2,932 Python files index in about 44 seconds on the test laptop.

2. Connect your agent

Client configuration
MCP toolWhat it gives the agent
mcm_searchDefinitions ranked by semantic, lexical, structural, symbolic and provenance channels.
mcm_impactPotential downstream consequences of a typed proposed change, before the edit.
mcm_contextA bounded, evidence-backed context package for the current task.
mcm_constraintsChecks against declared architectural constraints.
mcm_ingestIndexes or refreshes a repository from the agent session.

Use absolute paths for the MCP executable and database. Repository content stays in the local SQLite index unless you explicitly use external model-provider experiment scripts.

06 / EVIDENCE

The latest evidence is useful, mixed and narrower than the architecture

The current evaluation separates three questions: how efficiently context is retrieved, how accurately impact is predicted, and whether giving that tool to an agent improves the agent’s work. Those questions do not have the same answer.

10repositories in the complete feature-hashing suite
4repository size tiers across six ecosystems
23cross-file agent tasks found from 520 candidate commits
0.28paired sign-flip p-value in the agent-in-the-loop experiment

Context efficiency: signal exists

With the default feature-hashing provider, MCM is ahead of vector RAG on 7/10 repositories and level on 3/10; against the hybrid baseline it is ahead on 7/10 and level on 3/10. In the trained-embedding sweep it is ahead of vector RAG on 5/8 and level on 3/8.

The effect is not uniform

requests is a counterexample in both sweeps, and python-dotenv falls behind the best baseline with the trained embedding. Repository size appears relevant, but the current data do not establish size as the causal explanation.

Impact predictions are selective

The evaluation reports 0.88 precision for impact prediction over five repositories at a 7% firing rate. When the system makes a prediction it is often trustworthy, but it does not fire on most candidate changes.

Agent benefit: not demonstrated

The separate agent study does not establish that access to mcm_impact improves file selection. The apparent gain on four informative tasks disappears under the obvious usage check: most winning trials never called the tool.

p = 0.28 23 paired task deltas

The agent-in-the-loop result is a null

Across 23 tasks, three trials per condition produced 138 trials, six of which errored. Treatment was better on 5 tasks, worse on 2 and tied on 16, with mean paired delta +0.072. A two-sided sign-flip permutation test gives p = 0.28. The current experiment therefore cannot show that supplying impact analysis makes the agent perform better.

Only 9 of the 23 tasks were downstream consequences of the target—the class of problem propagation is designed to predict. Eleven were upstream co-requirements and three had no recorded edge.

Key limitations that still bound the claims

One horizon per repository

Within-repository variance is not measured even though the evaluation now spans four size tiers and six ecosystems.

Fitted weights overfit

MCM’s seven-parameter fitted weights improve the tuning repository but buy nothing on held-out data.

Feature hashing is the default

The default embedding is not a trained sentence model. The paired provider experiments show that this choice changes the comparison materially.

Python only

The parser and extractors remain Python-specific, and dynamic behavior still requires the runtime observation channel.

The full methods, bootstrap rules, tuning protocol, provider ablations and limitations are maintained in docs/evaluation.md.

Service interface

The HTTP surface, for calling MCM from a service. If you want to use MCM from a coding agent, you want the MCP server above instead — these routes are not what an agent speaks. Payloads below match the real request models in mcm/api/app.py.
